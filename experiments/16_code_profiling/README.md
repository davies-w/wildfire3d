# Experiment 16: code-level profiling for a 10× lot-simulation speedup

Measured outcome: uniform coarsening from 0.5 to 1 m gives 12.13x lower CPU cost, but changes the 30-second hot-case ignition label: the coarse case crosses the wall threshold at 23.0237 s, while the baseline does not. Raw west-face burning-rate data averaged over 20–30 s confirms positive burning only in the coarse case (maximum 4.7045e-5 kg/m2/s, versus zero baseline). This is not an acceptable fidelity-preserving 10x result. Passive OpenMP waiting reduces CPU consumption by 33.0% with identical recorded outputs but essentially unchanged elapsed time. Reduced radiation work saves only about 3% elapsed time and changes wall-temperature curves by up to 28.99 C. The longer baseline stopped cleanly at its one-hour case limit: last solver step 296.77233 s (last device sample 296.50856 s), 3604.10 elapsed seconds including stop/flush, and 12,468.29 process CPU-seconds (207.80 CPU-minutes). It did not complete the requested 600-second exposure.

The first wall-threshold event occurred at 213.868 simulated seconds, after approximately 8,604.32 CPU-seconds (143.41 CPU-minutes, interpolated from solver step CPU records). A positive ignition label is valid even though the run is incomplete; it is corroborated by raw west-wall burning-rate data averaged over 210–225 s (maximum 6.3036e-5 kg/m2/s; 12 positive samples). The 225 s upper bound includes the saved frame just after 220 s; using exactly 220 s can exclude that frame. Stopping at the first positive event would still require 28.68x less CPU to reach the 300-CPU-second goal for this case. A 10x reduction would yield about 14.34 CPU-minutes to that event. No general speedup or real-world ignition-accuracy guarantee follows from one workload.

The long profile contains 1,234,667 samples: 50.18% FDS, 44.03% OpenMP runtime, and 4.95% libc. Sampled CPU is within 0.03% of OS CPU. Its largest individual FDS leaf is 4.12% of sampled CPU. Cost per simulated second stays around 39–42 CPU-seconds through 210 simulated seconds, then rises to about 46–51 later; the longer exposure does not reveal a cheap late phase. No source patch has yet been timed.

The single cloud build and single Spot job are complete. The independent controller finished successfully; final inventory has zero VMs, disks, and Batch jobs. Rate-based build/worker estimate is USD0.1655 before credits; adding the full USD0.13 ancillary-charge contingency gives USD0.2955, below the USD0.45 approved allowance. These are estimates, not posted billing. See results/cost.json and results/cleanup.json.

Aim: measure function-level bottlenecks and actual process CPU consumption, then assess whether numerical/model simplifications or source changes could plausibly reduce total cost by tenfold. The eventual target is 300 CPU-seconds for a stated lot exposure, not merely five minutes of elapsed VM time.

Approved first-round allowance: USD0.45 total: one profiling build (20-minute maximum, USD0.12 allowance), one 4-vCPU Spot worker (under two hours including cleanup, USD0.20 allowance), and USD0.13 storage/transfer/control contingency. No automatic build/job retries and no on-demand fallback. This is a resource/runtime bound, not a Google dollar cap. Actual invoices lag.

FDS source revision: ff928dbf68a2623ced3a007be75391c6dc6c9f90. GNU optimized -O3 build, additionally -g -fno-omit-frame-pointer. gperftools CPU sampling at 99 Hz via LD_PRELOAD; flat/cumulative/function-line/call-graph reports. Process user+system CPU measured by wait4 independently of FDS routine timers, which use elapsed wall time. Cgroup throttling and context-switch evidence accompany each run. No privileged hardware counters are requested, so cache misses and memory bandwidth are not directly measured.

The 32×24×12 m, 0.5 m-grid workload derives from experiment 13. It includes a house, vegetation, surface spread, and embers. Its synthetic prescribed ignition/HRR surfaces remain unvalidated. Windows are corrected from combustible wood to an inert glass thermal layer; no glass-breakage claim. This is a performance workload, not a calibrated real-property training label generator. A separate prescribed 1.2 MW source near the house exercises a hotter regime without waiting for slow landscape spread. The coarser grid changes geometry snapping as well as resolution and cannot establish fidelity by itself.

Executed order: small profiler self-test; two identical unprofiled 30-second lot runs with a profiled counterpart between them; profiled/unprofiled 30-second hot exposure; passive OpenMP waiting, cheaper radiation and coarser-grid hot-exposure screens; a requested 600-second lot run if time remains. Every case is bounded. A stop-file cutoff is recorded as incomplete, never a negative ignition label. The long run reached its cutoff; its measured cost is only a lower bound for a complete 600-second simulation. Its observed positive event is sufficient for the binary label.

Results and profiles are uploaded after each case to survive later interruption. The independent workflow deadline performs job/VM cleanup even if the laptop disconnects. Raw evidence belongs in data/ and DVC. Matched FDS output is distinct from physical validation.

Inputs, decks, runner, cloud specification, profiling reports, and analysis reside in this experiment. Paid build/launch are explicit actions, excluded from automatic DVC reproduction.

The passive-wait candidate changes only runtime waiting behavior (OMP_WAIT_POLICY=PASSIVE, GOMP_SPINCOUNT=0), retaining four threads. This tests whether idle-thread busy-waiting consumes CPU during serial work; profiles and measured process CPU must confirm its effect. It does not change FDS physics settings.

Analysis dependencies: Python with numpy, matplotlib, PyYAML, and pyelftools 0.33. The raw sampling format is documented at https://gperftools.github.io/gperftools/cpuprofile-fileformat.html. Symbolization uses the exact downloaded profiling binary and verifies its SHA256 against each run. Shared libraries without their own debug symbols are attributed only to modules; legacy exported-symbol labels are not reliable descriptions of their internal work.

Local reproduction after the cloud run: `../../.venv/bin/dvc repro` from this directory restores the externally generated cloud evidence and runs analysis, symbolization, boundary verification, and plotting. It never launches paid cloud resources. The initial native preflight stage requires the repository's ARM FDS binary; boundary extraction requires fds2ascii (override its path with FDS2ASCII). Raw cloud input is cached with DVC; remote publication is a separate action.

The short hot baseline and passive-wait case produced byte-identical saved `.bf`, `.sf`, and `.prt5` evidence (five files). The full device time series also match. This does not validate the input material model against physical experiments, but isolates the observed CPU saving from changes to this simulation's recorded results.

Geometry confounds the uniform-coarsening comparison. `geometry.py` reads the solver's SMV obstruction grid indices: 15 of 17 obstruction bounds change. House height increases from 3.5 to 4 m; the roof loses its 0.5 m overhang; the prescribed source top rises from 0.5 to 1 m; and the nearest canopy's west-to-east extent ends at x=18 instead of 17.5, closing its 0.5 m wall gap. Several fences become zero-thickness mesh obstructions, which is not the same as removal. Therefore the different ignition label cannot be attributed solely to fluid discretization error. This is precisely why grid changes need geometry checks before use as training-data accelerations.

Scope limits: the geometry uses OBST, not GEOM, and does not exercise the earlier ember/GEOM failure. It is a small 32×24 m horizontal domain, not a complete neighborhood. The ignition devices use the deck's synthetic wall/roof thresholds (350/550 C); the half-meter baseline is a numerical reference, not established physical ground truth. An absolute five-CPU-minute goal also requires a physical exposure duration: this campaign requests 600 seconds for its longer reference, while the paired screens cover 30 seconds. Those durations must not be conflated.

A clean FDS stop-file cutoff can create a restart checkpoint even with a large DT_RESTART. The fetcher removes `.restart` members before local extraction/caching, retaining boundary, slice, particle, log, and profile evidence. If that occurs, `results/archive-cleanup-*.json` records the original cloud archive SHA256, removed members, and retained archive SHA256. The evidence manifest distinguishes the normalized local input from the original cloud archive.
