# Source inspection hypotheses, before sampling results

Pinned source ff928dbf68a2623ced3a007be75391c6dc6c9f90 under FDS/src/fds/Source.

- func.f90:23–26 implements CURRENT_TIME with MPI_WTIME. main.f90:3917–3941 writes routine durations derived from those wall timers. Use wait4 user+system CPU for the five-CPU-minute objective.
- fire.f90:89 onward scans the mesh for chemically active cells and then integrates active cells. The Cartesian loop around lines 252–269 is serial in this build; fire.o is not among the OpenMP-flagged objects in Build/makefile:153–162. Do not simply enable a directive: shared scratch arrays and mesh pointers require a thread-safety audit.
- divg.f90:788 onward repeatedly clears work arrays, allocates per-thread species scratch, computes mixture enthalpy, then computes face values. Profiles must establish whether property lookup, array traffic, allocation, or worksharing matters. No bandwidth counter data is available in this nonprivileged campaign.
- radi.f90:3707 onward performs radiation updates and directional sweeps. Upwind intensity dependencies constrain naive parallelization. Reduced angular resolution/update frequency is a physics approximation, not a free code optimization.
- Many OpenMP regions coexist with serial work. Sampling and a passive-wait comparison will test whether CPU burn in waiting threads is significant. This could improve CPU cost more than elapsed time.

These are hypotheses and code observations, not measured bottleneck findings. Populate measured priorities only after receiving profiles.

Additional source hypothesis: radi.f90:4408–4534 reconstructs diagonal grid slices inside each directional sweep, then enters a parallel region for each slice. The geometry/slice enumeration is mostly invariant. Candidates for later patches are caching those index lists and retaining a parallel team across slices while preserving the required upwind barrier. These are not implemented or timed in this round; the lot profile must first establish their relevance. Merely removing barriers would invalidate the dependency ordering.

Profiler verification: the smoke case produced 3434 samples at 10101 microseconds/sample, 34.69 sampled CPU-seconds versus 34.74 OS CPU-seconds. Thus the sampler covers aggregate thread CPU, not only elapsed time or the main thread. The shipped legacy google-pprof labels stripped shared-library addresses with nearby exported names; those names must not be interpreted literally. symbolize.py instead reports library-level attribution for shared objects and exact ELF/DWARF attribution for FDS, cross-checked against the same 3434 samples. Source-line results reflect optimized/inlined code.

First completed lot baseline: 30 physical seconds, 345.706 elapsed seconds, 1252.110 process CPU-seconds, 1379 timesteps. FDS wall-timer shares: divergence 36.0%, mass 16.3%, velocity 14.1%, radiation 8.8%, combustion 7.8%, pressure 4.8%, wall thermal work 5.0%. These are broad phase timings, not exclusive CPU samples. At this early rate, 600 simulated seconds would cost approximately 25,042 CPU-seconds (83.5 times a 300-CPU-second target); this is only a projection until a longer exposure is measured. A 10× reduction and the five-CPU-minute target are separate tests.

Measured lot profile (30 s, 122204 samples): FDS 52.26%, libgomp 43.07%, libc 3.69%. Sampled CPU 1234.383 s versus wait4 CPU 1234.218 s. About 27.32% of all samples are in OpenMP stacks without an FDS caller; another 4.14% are OpenMP samples with the species-advection wall-loop caller, and 3.45% with the mass-flux wall-loop caller. This supports testing waiting/worksharing overhead but does not identify every runtime sample as removable spin time. The unprofiled and profiled lot device outputs match at recorded precision; their elapsed/CPU times differ by about 1.5%, which must be interpreted alongside the second baseline repeat.

Highest exclusive FDS functions: scalar face reconstruction 4.16%, radiation sweep 4.10%, species advection 3.54%, one divergence worker 3.34%, species sensible enthalpy interpolation 2.65%. Cumulative functions overlap and must not be summed. Even eliminating the entire measured libgomp CPU share at otherwise fixed work would yield only 1/(1-0.4307)=1.76× CPU reduction, not 10×.

Source follow-up: GET_SCALAR_FACE_VALUE in func.f90:1286 creates an OpenMP parallel region with IF(I2>1). It is also called for tiny wall-adjacent stencils from inside outer parallel wall loops (mass.f90:88 onward, divg.f90:1016 onward). An explicit serial small-stencil path could avoid serialized/nested runtime setup without changing the flux limiter. This is a concrete later source-patch candidate, not an implemented speedup. Larger face loops are already parallel and must retain dependency-correct behavior.

Thermodynamic lookup is already tabulated: func.f90:1787 interpolates H_SENS_Z, and nearby heat-capacity routines use CP_Z tables. A proposal to replace all thermodynamics with lookup tables would duplicate existing work. Cell-level reuse/fusion is a narrower hypothesis, requiring profiling and conservation/output checks.

Boundary verification for lot_a versus lot_profile: fds2ascii extracted 136 main-structure west-plane samples (x=18, y=8..16,z=0..3.5) averaged over 20–30 s. Both ranges are 20.312–24.689 °C. Device series match exactly at recorded precision. These are still early, low-building-exposure samples; the separate hot case is required before generalizing their timing distribution to building ignition.

Compiler provenance from the executable's DWARF: GNU Fortran 14.2.0, -O3, -g, -fno-omit-frame-pointer, -march=x86-64, -mtune=generic. A separate CPU-targeted optimized build is a later candidate; it is not equivalent to the existing baseline and has not been timed. Building with -march=native on a Cloud Build worker would target that builder rather than necessarily the eventual C3 worker, so any such comparison must specify and verify the intended target ISA. No fast-math transformation is used in this campaign.

Selective-resolution limitation verified in the pinned source: main.f90:779–792 gathers mesh timestep requests and sets the shared DT to MINVAL(DT_NEW); velo.f90:3188–3205 applies flow, diffusion, and particle stability limits. Retaining a fine mesh can therefore keep the global timestep small even when much of the domain is coarsened. Selective resolution saves cells, but does not automatically obtain the timestep gain of uniform coarsening.

For intuition only, a model with fixed fine-grid timestep and uniform per-cell cost gives speedup 1/[f+(1-f)/8] when fraction f of the original volume remains fine and the rest doubles cell width. At f=0.10 this is 4.71x, before communication and unequal physical workloads. This is an idealized work-count estimate, not a measured FDS speedup or fidelity guarantee. Uniform coarsening can also increase the timestep, whereas a fine island can prevent that gain. Hardware/compiler gains and runtime waiting savings cannot safely be multiplied into this estimate without a combined benchmark.

Task-specific early termination is a distinct candidate: for the user's binary label (any main-structure ignition), a valid positive event is sufficient and subsequent simulation is unnecessary. ctrl.f90:258–274 already supports a KILL control; an ANY aggregation of the ignition devices could feed it in a later input deck. This is not enabled in this profiling campaign, because its purpose includes observing later work. Negative labels still require the full chosen exposure horizon. Speedup depends on the distribution of first-ignition times, and cannot be claimed from a single positive case. analyze.py estimates CPU consumed at the first logged event from the FDS step CPU series.
